# TechStack Compass

AI 时代的产品工程技术栈避坑指南。

一句话：用场景选择技术栈，而不是用流行词选择技术栈。

这个项目整理产品级项目从 0 到 1 最容易缺失的工程判断：什么时候用什么技术栈、高并发怎么判断、Python 多线程到底卡在哪里、容灾怎么做、上线前要检查什么。

它不是“最全资料合集”。它更像一张工程决策地图：短句、表格、检查清单、反例和可执行边界。

## 适合谁

- 想快速补齐技术栈知识面的开发者。
- 正在从 0 到 1 做 Web、SaaS、AI、App、内部工具的工程师。
- 需要判断“这个项目该用什么栈”的产品技术负责人。
- 用 AI 写代码，但希望自己能判断技术取舍和生产坑点的人。

## 60 秒决策

| 你要做什么 | 默认起步方案 | 先别急着上 |
| --- | --- | --- |
| 普通 SaaS / 管理后台 | React/Vue + FastAPI/NestJS/Spring/.NET + Postgres | 微服务、Kafka、异地多活 |
| AI 应用 / Agent / RAG | Next.js/React + Python FastAPI + Postgres + Redis + 对象存储 | 复杂平台、全量自动化、无评估上线 |
| 高并发 API | Go/Java 常见；Python/Node 也能做 I/O 型服务 | 只靠“多线程”解决 CPU 瓶颈 |
| 内容站 / 官网 | Next.js/Nuxt/Astro + Markdown/CMS + CDN | 重后台、复杂数据库设计 |
| 电商 / CMS | Laravel/WordPress + MySQL/Postgres + Redis + 对象存储 | 自研所有 CMS 能力 |
| 桌面开发者工具 | Tauri/Electron + SQLite + 本地文件能力 | 只是网页套壳却做桌面 |
| 数据分析 / 报表 | Postgres 起步；数据量上来再接 ClickHouse | 一开始就复杂数仓 |
| 搜索功能 | Postgres 全文搜索起步；体验要求高再接 OpenSearch/Elasticsearch | 把搜索引擎当主数据库 |
| 异步任务 | 数据库任务表起步；稳定后 SQS/RabbitMQ；事件流再 Kafka | 小任务直接上 Kafka |

## 核心原则

1. 团队会不会，比理论最优更重要。
2. 产品需不需要，比技术流行更重要。
3. 上线快不快，比架构完整更重要。
4. 以后能不能换，比现在看起来高级更重要。
5. 先跑通核心链路，再补稳定性、安全性和可观测性。
6. 高并发首先是系统设计问题，其次才是语言选择问题。
7. 容灾不是买了高可用服务就结束，必须能恢复、能演练、能定位。
8. AI 项目不能只看模型效果，还要看成本、评估、隐私、兜底和人审边界。

## 和普通资料合集的区别

| 普通资料合集的问题 | 本项目的做法 |
| --- | --- |
| 链接很多，但不知道什么时候用 | 按场景给“什么时候用 / 什么时候别用 / 常见坑 / 替代方案” |
| 只讲概念，不讲生产坑 | 每个主题补充上线、故障、扩容、维护的坑点 |
| 只适合学习，不适合做项目 | 保留从 0 到 1 的交付物和检查清单 |
| 说法极端，比如“Python 不能高并发” | 解释边界：I/O、CPU、GIL、多进程、缓存、队列、水平扩容 |
| README 很长但不可导航 | README 做入口，深内容拆到 docs |

## 项目目标

这个项目的目标是成为中文开发者真正愿意收藏、反复查、持续贡献的高星技术栈知识库。

高星不是靠包装出来的，而是靠三件事：

- 内容能直接帮人做技术判断。
- 结论有边界，不把复杂问题讲成口号。
- 读者遇到真实项目坑点时，会想到回来查。

已完成：

- 技术栈选择总览。
- 高并发和 Python GIL 解释。
- 容灾、可靠性和监控清单。
- 产品级从 0 到 1 工程路线。
- 上线前 50 项检查。

下一步：

- 增加 AI 应用工程专题：RAG、Agent、评估、成本、隐私。
- 增加更多真实架构案例。
- 增加贡献者提交模板和内容审核标准。
- 增加英文摘要，方便非中文开发者理解项目价值。
