# 第 3 章 高并发与 Python 多线程误区

很多人说：“高并发不能用 Python，因为 Python 的 multithread 并不是真多线程。”

这句话只说对了一半。

更准确的说法是：

```text
CPython 单进程多线程不适合 CPU 密集型并行计算。
但 Python 可以通过异步 I/O、多进程、队列、缓存、数据库优化和水平扩容支撑很多高并发 Web 业务。
```

## 本章第一性原理

高并发不是语言标签问题，而是资源排队问题。

一个请求会消耗 CPU、内存、连接池、数据库、缓存、队列、网络和下游服务。任何一个环节成为瓶颈，系统都会开始排队。排队变长，延迟升高。延迟升高，并发堆积。并发堆积，系统雪崩。

所以高并发的第一步不是换语言，而是找到真正排队的位置。

## 高并发到底在解决什么

高并发不是“很多请求同时来”这么简单。

它通常在解决：

- 吞吐量：单位时间处理多少请求，比如 QPS、TPS。
- 延迟：用户等多久，比如 P95、P99。
- 连接数：同时维持多少连接，比如 WebSocket、下载、长轮询。
- 峰值流量：突然来了 10 倍流量会不会崩。
- 成本：同样流量需要多少机器、数据库、缓存和云费用。

目标是：

```text
在可接受成本下，让系统稳定处理更多请求，并且响应时间可控。
```

## QPS 和并发不是一回事

公式：

```text
并发数 ≈ QPS × 平均响应时间
```

例如：

```text
QPS = 1000
平均响应时间 = 0.2 秒
并发数 ≈ 200
```

如果响应时间变成 2 秒：

```text
QPS = 1000
平均响应时间 = 2 秒
并发数 ≈ 2000
```

响应越慢，同样 QPS 下堆积越严重。

## Python 线程和 GIL

CPython，也就是最常用的 Python 实现，有一个 GIL，全局解释器锁。

它的效果是：

```text
同一个 Python 进程里，多个线程不能同时执行 Python 字节码。
```

所以如果 4 个 Python 线程都在做纯 CPU 计算，它们通常不能真正跑满 4 个 CPU 核心。

### GIL 影响大的任务

- 图片处理。
- 视频转码。
- 大量加密解密。
- 大规模 JSON 计算。
- 机器学习前处理。
- 复杂算法计算。
- 纯 Python 写的 CPU 密集任务。

这些任务的瓶颈在 CPU。Python 多线程通常不会随着线程数增加而明显变快。

### GIL 影响小的任务

- 查询数据库。
- 调用 Redis。
- 请求外部 API。
- 读写文件。
- 网络 I/O。
- 等待下游服务返回。

这些操作大部分时间在等 I/O。线程等待 I/O 时，GIL 可以释放，其他线程可以继续执行。

所以：

```text
Python 多线程不适合提升 CPU 并行计算能力，但可以处理很多 I/O 等待型并发。
```

## 语言在高并发下的边界

| 技术 | 适合 | 边界 |
| --- | --- | --- |
| Python / FastAPI | AI 应用接口、数据服务、I/O 密集 API、快速迭代业务 | CPU 密集任务要多进程、C/Rust 扩展、任务队列或拆服务 |
| Node.js | I/O 密集 API、实时应用、WebSocket、BFF | JS 主线程 CPU 计算会阻塞事件循环 |
| Go | 高并发 API、网关、微服务、云原生服务 | 复杂业务抽象和快速 CRUD 不一定最省力 |
| Java | 大型业务系统、高并发复杂业务、金融电商 | 项目容易变重，调优复杂度较高 |
| Rust | 极致性能、系统组件、代理、网关、安全边界 | 学习和开发成本高，不适合普通业务 MVP |

真实项目里，瓶颈经常不是语言，而是：

```text
数据库、缓存、锁、慢查询、连接池、外部 API、网络、部署参数。
```

## Python 高并发常见部署

```text
Nginx / Load Balancer
  -> Gunicorn / Uvicorn 多 worker
  -> FastAPI
  -> Redis / DB / MQ / Object Storage
```

关键点：

- 多 worker 是多进程，每个进程有自己的 GIL。
- worker 不是越多越好，要看 CPU、内存、连接数和下游容量。
- I/O 型接口可以考虑 async。
- CPU 型任务不要同步卡住请求，放队列或拆服务。

## 扩容路线

不要一上来就换语言。

### 1. 先定位瓶颈

看：

- 慢接口。
- 慢 SQL。
- CPU 使用率。
- 内存使用。
- 数据库连接池。
- Redis 命中率。
- 队列堆积。
- 下游 API 延迟。
- 锁等待。

没有指标的优化，大多是在猜。

### 2. 单机优化

先清掉低成本问题：

- N+1 查询。
- 重复计算。
- 大对象返回。
- 不必要的同步调用。
- 过多日志。
- 慢 SQL。
- 锁粒度太大。

### 3. 异步 I/O

适合：

```text
请求很多，但每个请求大部分时间都在等数据库、Redis、HTTP 或文件 I/O。
```

不适合：

```text
每个请求都要做大量 CPU 计算。
```

### 4. 多进程

Python 想利用多核，常见方式是多进程。

示例：

```bash
gunicorn -w 4 -k uvicorn.workers.UvicornWorker app:app
```

注意：

- worker 数和 CPU 核数、内存、连接池一起算。
- worker 太多会增加上下文切换和资源消耗。

### 5. 水平扩容

结构：

```text
负载均衡
  -> 服务实例 1
  -> 服务实例 2
  -> 服务实例 3
```

前提：

- 服务尽量无状态。
- session 放 Redis 或用 token。
- 文件上传到对象存储。
- 配置统一管理。
- 日志和监控集中化。

### 6. 队列削峰

适合：

- 发短信。
- 发邮件。
- 生成报表。
- 视频处理。
- 订单后续流程。
- AI 任务。
- 日志处理。

结构：

```text
用户请求
  -> 写入任务队列
  -> 后台 worker 处理
```

队列的价值是把瞬时高峰变成可控速度。

### 7. 缓存

适合缓存：

- 读多写少的数据。
- 首页配置。
- 商品详情。
- 用户权限。
- 热门榜单。
- 字典表。
- 计算结果。

注意：

- 缓存穿透。
- 缓存击穿。
- 缓存雪崩。
- 热 key。
- 数据一致性。

### 8. 数据库优化

很多系统最后卡在数据库。

优先看：

- 索引。
- 慢 SQL。
- N+1 查询。
- 深分页。
- 连接池。
- 大事务。
- 长时间锁表。
- 批量写入。
- 读写分离。

数据库优化通常比换语言更有效。

### 9. 限流、熔断、降级

系统不可能无限承载流量。

限流：

```text
每个用户每秒最多 10 次请求。
```

熔断：

```text
下游服务已经很慢，就暂时不再继续打它。
```

降级：

```text
推荐系统挂了，就返回默认推荐。
```

目标是保住核心链路，不让局部故障拖垮整个系统。

## 常见坑

### 只加机器，不查瓶颈

如果瓶颈在数据库，加应用机器可能更糟。更多应用实例会打出更多数据库请求，结果是数据库被打挂。

### 数据库连接池太小或太大

连接池太小，请求都在等连接。连接池太大，数据库连接被打满。

连接池要和应用实例数、worker 数、数据库最大连接数、单请求 SQL 数一起算。

### N+1 查询

错误：

```text
查 100 个订单。
每个订单再查一次用户。
总共 101 次查询。
```

正确方向：

```text
批量查询、join、预加载、缓存。
```

### 锁用错

常见问题：

- 全局锁。
- 分布式锁粒度太大。
- 锁内做慢操作。
- 锁内调用外部 API。
- 事务时间太长。
- 热点数据频繁更新。

锁会让并发变串行。锁要尽量小、短、少。

### 同步外部 API

如果每个请求都同步调用第三方 API，你的系统性能取决于对方。

要做：

- 超时。
- 重试上限。
- 缓存。
- 队列。
- 熔断。
- 降级。

## 场景怎么选

| 场景 | 推荐判断 |
| --- | --- |
| 普通后台管理系统 | Python/FastAPI、Django、Java/Spring、.NET 都可以。重点是权限、SQL、可维护性。 |
| 高流量内容详情页 | 语言不是第一瓶颈。重点是 CDN、Redis、本地缓存、数据库索引、限流。 |
| WebSocket 聊天服务 | Go、Node.js、Java 更常见。重点是连接管理、心跳、消息队列、在线状态。 |
| AI 图片生成任务 | Python 很适合，但请求不要同步等生成完成。API 入队，worker 处理，前端轮询或 WebSocket。 |
| 大量 CPU 计算 | Go、Java、Rust 更合适。Python 要用 multiprocessing、C/Rust 扩展、NumPy 或独立计算服务。 |
| 秒杀系统 | Go/Java 常见，Python 可做外围服务。重点是限流、排队、缓存库存、异步下单、幂等、热点隔离。 |

## 一句话总结

高并发首先是系统设计问题，其次才是语言选择问题。

成熟的判断不是“某语言能不能高并发”，而是：

```text
瓶颈在哪里？
请求是在等 I/O，还是在吃 CPU？
能不能缓存？
能不能异步？
能不能削峰？
数据库能不能扛住？
失败时系统会不会雪崩？
```
