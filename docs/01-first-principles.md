# 第 1 章 第一性原理：技术选型到底在选什么

技术选型不是“哪个技术更高级”，而是判断系统真正需要解决什么问题。

你要先拆开几个基本问题：

- 计算怎么做。
- 状态放哪里。
- 反馈速度有多重要。
- 风险能不能承受。
- 成本是否匹配。
- 团队是否用得起来。
- 未来能不能替换。

一个技术栈好不好，不取决于它强不强，而取决于它是否匹配当前阶段最重要的约束。

## 技术栈的七个底层约束

| 约束 | 真正要问的问题 | 典型误判 |
| --- | --- | --- |
| 计算 | 主要瓶颈是 CPU、I/O、网络、数据处理，还是下游等待 | 看到高并发就换语言 |
| 状态 | 数据是否长期保存，是否需要事务，是否能丢，是否强一致 | 把缓存、搜索引擎、对象存储当主数据库 |
| 反馈速度 | 从写代码到上线验证要多久 | 为未来规模牺牲当前迭代速度 |
| 风险 | 哪种错误最不能接受 | 只优化性能，忽略数据错和权限错 |
| 成本 | 机器、人力、学习、维护、迁移哪个最贵 | 只算云费用，不算排障和维护 |
| 团队能力 | 团队会不会，能不能排查，新人能不能接手 | 选了理论最优但团队用不对 |
| 可替换性 | 以后换起来难不难 | 业务逻辑深度绑死框架或平台 |

## 1. 为什么 0 到 1 默认关系型数据库

**表层说法**

```text
关系型数据库太传统了。
现在是不是应该直接用 NoSQL？
以后数据量大了，Postgres/MySQL 会不会扛不住？
```

**第一性原理**

0 到 1 阶段最重要的问题通常不是海量数据，而是状态正确。

早期业务有几个特征：

- 数据模型还在变化。
- 业务规则还没稳定。
- 很多操作需要事务。
- 数据不能乱。
- 查询方式还不完全确定。
- 团队需要快速理解和排查数据问题。

关系型数据库的核心价值不是“老”，而是它提供了可靠的数据结构、事务、一致性、索引、查询能力和成熟生态。

早期系统最怕的不是数据库性能不够，而是数据关系混乱、业务状态错误、问题查不清楚。

**真实选择**

默认选 Postgres 或 MySQL。

如果没有非常明确的理由，不要一开始就把核心业务数据放进 NoSQL、搜索引擎、缓存或对象存储里当主数据库。

更实际的顺序：

1. 用关系型数据库承载核心业务状态。
2. 用索引、分页、读写拆分、缓存解决逐步出现的性能问题。
3. 当某类数据确实不适合关系模型时，再引入专门系统。

关系型数据库不是保守选择，而是早期系统降低状态风险的默认选择。

## 2. 为什么高并发常常不是语言问题

**表层说法**

```text
Java 比 Python 更适合高并发。
Go 并发强，所以换 Go 就能解决性能问题。
Node.js 是异步的，所以一定能扛高并发。
```

**第一性原理**

高并发的瓶颈通常不只在语言，而在整个请求链路：

- 数据库连接是否耗尽。
- SQL 是否慢。
- 是否有热点数据。
- 是否大量请求在等外部接口。
- 是否存在锁竞争。
- 缓存是否命中。
- 队列是否堆积。
- 服务是否能水平扩展。
- 网络、磁盘、内存是否成为瓶颈。
- 代码是否把慢操作放在同步路径上。

很多业务请求的主要时间不是 CPU 执行代码，而是在等数据库、网络、磁盘、第三方接口或锁。

这时换语言不一定解决问题，因为真正慢的部分不在语言运行速度。

**真实选择**

遇到高并发问题，先做观测，再做判断：

1. 看请求耗时分布。
2. 看数据库慢查询。
3. 看连接池、线程池、队列长度。
4. 看 CPU、内存、磁盘、网络。
5. 看缓存命中率。
6. 看外部依赖耗时。
7. 看是否可以异步化、批处理、限流或削峰。

如果瓶颈是数据库，换语言没用。

如果瓶颈是外部接口，换语言没用。

如果瓶颈真的是 CPU 密集计算，再考虑语言、运行时、并行模型或专门的计算服务。

## 3. 为什么 Python 多线程不是 CPU 并行答案

**表层说法**

```text
Python 有 GIL，所以不适合并发。
Python 多线程没用。
AI 都用 Python，所以 Python 性能一定很强。
```

**第一性原理**

CPython 有 GIL，也就是全局解释器锁。它会让多个 Python 线程很难同时执行 Python 字节码里的 CPU 计算。

所以，如果任务是纯 CPU 计算，比如大量数学运算、图像处理、压缩、模拟计算，只靠 Python 多线程通常不能真正吃满多个 CPU 核心。

但这不代表 Python 不适合并发，也不代表 Python 不适合 AI 和 Web。

因为很多场景的瓶颈不是 Python 解释器执行 CPU 代码：

- Web 服务经常在等数据库、网络、文件、第三方 API。
- I/O 等待期间，线程或异步模型可以切换处理其他请求。
- AI 训练和推理的大量计算通常交给 GPU、CUDA、PyTorch、TensorFlow、NumPy 等底层库。
- 这些底层库很多是 C/C++/Fortran/CUDA 实现，不靠 Python 解释器逐行算。

Python 在这些场景里更像胶水语言和业务编排语言。

**真实选择**

Web I/O 型服务可以用 Python。

CPU 密集任务优先考虑：

- 多进程。
- C/C++/Rust 扩展。
- NumPy、PyTorch 等底层计算库。
- 任务队列。
- 专门的计算服务。
- GPU 加速。

结论不是“Python 快”或“Python 慢”，而是：

```text
Python 不适合用多线程解决纯 CPU 并行，但适合 AI 生态、Web I/O、数据处理编排和快速迭代。
```

## 4. 为什么 Redis 不能早上

**表层说法**

```text
加 Redis 可以提升性能。
缓存一下就快了。
以后高并发肯定要用 Redis。
```

**第一性原理**

Redis 是缓存和高速状态存储，不是免费的性能按钮。

引入 Redis 后，系统会多出新的问题：

- 缓存和数据库一致性。
- 缓存穿透、击穿、雪崩。
- key 设计和过期策略。
- 热点 key。
- Redis 挂掉后的降级。
- 数据是否允许丢失。
- 缓存更新时机。
- 运维和监控成本。

如果早期访问量不高，数据库本身能扛住，引入 Redis 可能不会让系统更可靠，反而会让状态变复杂。

**真实选择**

顺序应该是：

1. 先用数据库和合理索引。
2. 发现明确的读性能瓶颈。
3. 判断数据是否适合缓存。
4. 设计缓存失效和降级策略。
5. 再引入 Redis。

Redis 应该为明确问题服务，而不是为架构显得完整服务。

## 5. 为什么 Kafka 不能早上

**表层说法**

```text
Kafka 可以解耦系统。
用消息队列更专业。
以后流量大了，肯定要 Kafka。
```

**第一性原理**

Kafka 解决的是高吞吐、持久化、可回放的事件流问题。

它很强，但会引入复杂性：

- 消息顺序。
- 重复消费。
- 消费失败。
- 幂等处理。
- 消息堆积。
- topic 和分区设计。
- 消费者组管理。
- 延迟和可观测性。
- 业务状态与消息状态的一致性。

很多早期系统的问题不是缺少消息队列，而是业务流程还没稳定。

同步调用的问题容易看见：请求失败就是失败。

异步消息的问题更隐蔽：消息可能晚到、重复到、乱序到，或者消费了一半失败。

**真实选择**

更好的顺序：

1. 先用清晰的同步流程实现核心业务。
2. 对非关键路径任务使用简单异步任务。
3. 当确实需要削峰、解耦、事件回放或高吞吐流处理时，再引入 Kafka。
4. 引入 Kafka 时，先设计幂等、重试、死信、监控和补偿。

Kafka 不是高级异步，而是事件流基础设施。

## 6. 为什么微服务不能早上

**表层说法**

```text
微服务更灵活。
微服务方便扩展。
大厂都用微服务，所以我们也应该用。
```

**第一性原理**

微服务解决的是大型系统的组织问题，不只是技术问题。

它真正要处理的是：

- 多团队协作。
- 服务边界清晰。
- 独立部署。
- 独立扩容。
- 故障隔离。
- 不同模块有不同技术需求。
- 不同团队有不同交付节奏。

但它也会带来：

- 服务发现。
- 配置管理。
- 链路追踪。
- 接口版本。
- 分布式事务。
- 网络故障。
- 部署复杂度。
- 数据一致性。
- 跨服务调试。
- 团队沟通成本。

如果团队很小，业务还没定型，服务边界也不清楚，微服务通常会把一个简单问题拆成多个分布式问题。

**真实选择**

0 到 1 阶段通常更适合模块化单体。

模块化单体不是低级架构。它是在一个应用里保持清晰模块边界，让系统先容易开发、测试、部署和理解。

顺序：

1. 先做模块化单体。
2. 在代码里保持清晰边界。
3. 当某个模块有独立扩容、独立部署或独立团队维护需求时，再拆服务。
4. 拆服务前先明确数据边界和接口契约。

## 7. 为什么异地多活不能早上

**表层说法**

```text
异地多活可靠性最高。
系统要稳定，就应该多机房、多地域。
万一一个地区挂了怎么办？
```

**第一性原理**

异地多活解决的是极高可用和灾难恢复问题，但最难的部分不是部署多份服务，而是状态一致性。

复杂点在：

- 数据如何跨地域同步。
- 延迟如何处理。
- 写冲突如何解决。
- 用户请求路由到哪里。
- 一个地域故障时如何切流。
- 故障恢复后数据如何对账。
- 哪些业务允许最终一致。
- 哪些业务必须强一致。
- 演练和监控如何做。
- 成本是否值得。

很多团队以为自己在买可靠性，实际可能是在引入更难排查的数据一致性风险。

**真实选择**

早期系统通常不应该直接做异地多活。

更合理的路径：

1. 单区域内做好备份、监控、告警和自动恢复。
2. 数据库做高可用和定期备份。
3. 做清晰的故障恢复流程。
4. 做跨区域冷备或热备。
5. 业务规模和可用性要求足够高时，再考虑异地多活。
6. 在异地多活前，先明确 RTO 和 RPO。

异地多活不是稳定性的起点，而是高成熟度系统在明确成本和风险后的选择。

## 一句话总结

表层说法：

```text
技术栈要先进、可扩展、高性能。
```

第一性原理：

```text
技术栈的本质是用有限的人力、时间和成本，管理计算、状态、反馈速度和风险。
```

真实选择：

```text
早期系统优先选择简单、成熟、团队能掌控、未来可替换的技术。
等瓶颈真实出现，再为具体问题引入具体技术。
```
