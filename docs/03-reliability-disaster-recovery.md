# 容灾与生产可靠性

容灾、高可用、故障恢复，本质都在回答：

```text
系统出问题时，业务还能不能继续跑？
如果不能，多久能恢复？
会丢多少数据？
```

产品级项目不能只考虑“功能能不能做出来”，还要考虑“上线后坏了怎么办”。

## 高可用和容灾的区别

| 概念 | 关注点 | 目标 |
| --- | --- | --- |
| 高可用 | 故障时服务不中断 | 少宕机，少中断 |
| 容灾 | 故障后如何恢复 | 坏了以后能救回来 |
| 备份 | 数据能不能找回来 | 防止数据彻底丢失 |
| 灰度/回滚 | 发布出错怎么办 | 降低上线事故影响 |

一句话：

```text
高可用是“别停”，容灾是“停了也能救回来”。
```

## 核心指标

### SLO

Service Level Objective，服务等级目标。

例子：

- 每月可用性不低于 99.9%。
- 99.9% 的请求在 300ms 内返回。
- 核心下单接口错误率低于 0.1%。

SLO 是内部目标，用来指导工程建设。

### SLA

Service Level Agreement，服务等级协议。

它通常是对客户、用户、合作方承诺的服务标准，可能和合同、赔偿责任有关。

### RTO

Recovery Time Objective，恢复时间目标。

表示故障后最多允许多久恢复服务。

- RTO = 5 分钟：5 分钟内必须恢复。
- RTO = 1 小时：1 小时内恢复可以接受。
- RTO 越短，成本越高。

### RPO

Recovery Point Objective，恢复点目标。

表示故障后最多允许丢多少数据。

- RPO = 0：不允许丢数据。
- RPO = 1 分钟：最多丢最近 1 分钟数据。
- RPO 越小，成本越高。

### 错误预算

如果月可用性目标是 99.9%，每月允许约 43 分钟不可用。

这段时间就是错误预算。

错误预算快耗尽时，应减少冒险发布，优先修稳定性问题。

## 常见架构

| 架构 | 适合 | 风险 |
| --- | --- | --- |
| 单区 | 早期项目、内部工具、测试环境 | 机房或区域故障可能整体不可用 |
| 同城多可用区 | 大多数生产级互联网应用 | 成本中等，需要多副本和流量切换 |
| 异地多活 | 大型互联网、金融、支付、全球化 | 成本高，数据一致性和运维复杂 |
| 主备 | 数据库、核心服务故障接管 | 切换失败、复制延迟、脑裂 |
| 读写分离 | 读多写少系统 | 主从延迟，写后读可能读不到 |
| 冷备 | 非核心系统、预算有限 | 恢复慢，文档和备份可能不可用 |
| 热备 | 核心业务、停机敏感服务 | 成本高，需要持续演练 |

从 0 到 1 不要一开始做异地多活。先做好备份、恢复演练、多实例、限流、回滚。

## 最低成本容灾清单

### 基础部署

- 应用至少部署 2 个实例。
- 使用负载均衡分发请求。
- 应用实例尽量无状态。
- 配置健康检查。
- 进程崩溃后能自动重启。
- CPU、内存、磁盘有基础监控。

### 数据库

- 数据库必须有自动备份。
- 备份不能只放在同一台机器上。
- 备份保留多个时间点。
- 至少每月做一次恢复演练。
- 重要数据有操作审计。
- 危险删除尽量软删除。
- 生产迁移前先备份。

### 发布

- 发布前有基本测试。
- 发布后能快速回滚。
- 高风险功能先灰度。
- 每次发布记录版本号、时间、负责人。
- 发布失败能定位到具体版本。

### 接口调用

- 所有外部接口必须设置超时。
- 所有重试必须有次数限制。
- 重试要加退避和随机抖动。
- 支付、订单、发货等操作必须幂等。
- 第三方 API 不可用时有降级方案。

### 缓存和队列

- 缓存失效要防止击穿。
- 热点 key 要有保护。
- 队列消费失败要能重试。
- 多次失败后进入死信队列。
- 死信队列要有人处理。
- 消息处理必须幂等。

### 监控告警

- 服务不可用要告警。
- 错误率异常要告警。
- 延迟升高要告警。
- 数据库连接数异常要告警。
- 磁盘快满要告警。
- 告警要有人接收。
- 告警要能定位问题。

## 数据层容灾

应用坏了可以重启。数据丢了，问题就大了。

### 备份

备份要考虑：

- 备份频率。
- 备份保留时间。
- 备份存放位置。
- 备份是否加密。
- 备份是否能恢复。
- 恢复需要多久。
- 是否覆盖核心数据和数据库结构。

常见策略：

- 每天全量备份。
- 高频业务增加增量备份。
- 保留 7 天、30 天或更久。
- 备份放到不同机器或不同存储。
- 重要系统做跨地域备份。

### 恢复演练

只有备份，没有恢复演练，等于没有容灾。

恢复演练要验证：

- 备份文件是否完整。
- 数据库能否成功恢复。
- 恢复后数据是否正确。
- 恢复过程需要多久。
- 应用能否连接恢复后的数据库。
- 恢复文档是否能照着执行。

最好让非原开发也能按文档恢复。否则人也是单点风险。

### 复制延迟

主从复制、跨机房同步、读写分离都可能有复制延迟。

风险：

- 用户刚提交的数据查不到。
- 订单状态不一致。
- 后台看到旧数据。
- 故障切换后丢失部分数据。

处理：

- 强一致场景读主库。
- 写后短时间读主库。
- 从库延迟过高时自动摘除。
- 监控主从延迟和复制中断。

### 幂等

幂等是：

```text
同一个操作执行一次和执行多次，结果应该一致。
```

例子：

- 同一个订单不能重复扣款。
- 同一条消息不能重复发货。
- 同一个退款请求不能重复退款。
- 同一个注册请求不能创建多个账号。

做法：

- 唯一请求 ID。
- 业务唯一键。
- 数据库唯一索引。
- 操作前检查状态。
- 消息消费记录处理状态。
- 去重表。

### 死信队列

消息消费失败后，不应该无限重试。

做法：

- 失败后重试几次。
- 每次重试间隔逐渐变长。
- 超过次数后进入死信队列。
- 死信队列单独告警。
- 修复问题后支持重新投递。

死信队列不是垃圾桶。进去的消息要有人看、有人处理、有人复盘。

## 应用层容灾

### 健康检查

区分：

- 存活检查：进程还在不在。
- 就绪检查：服务是否准备好接流量。
- 依赖检查：数据库、缓存、队列是否可用。

健康检查要轻量，不要做复杂查询。

### 自动重启

常见方式：

- systemd。
- Docker restart policy。
- Kubernetes Deployment。
- 进程管理工具。

自动重启不能替代根因修复。服务不停重启必须告警。

### 限流

限流对象：

- IP。
- 用户。
- 接口。
- 租户。
- API Key。
- 业务操作。

限流不是为了拒绝用户，而是保护系统，让核心服务还能活着。

### 熔断

当下游服务持续异常时，暂时停止调用它。

熔断后可以：

- 快速失败。
- 返回默认值。
- 走降级逻辑。
- 等一段时间后再尝试恢复。

### 降级

牺牲非核心功能，保住核心功能。

例子：

- 推荐服务挂了，展示默认列表。
- 评论服务异常，先隐藏评论。
- 实时统计异常，展示离线数据。
- 短信服务异常，切换备用通道。

降级要提前设计，事故时临时写通常来不及。

### 重试

重试要谨慎。

错误做法：

- 无限重试。
- 立即重试。
- 所有服务一起重试。
- 没有超时还重试。
- 非幂等操作直接重试。

正确做法：

- 最大重试次数。
- 指数退避。
- 随机抖动。
- 只对可重试错误重试。
- 重试操作必须幂等。

### 超时

所有远程调用都必须设置超时：

- HTTP 请求。
- RPC 请求。
- 数据库查询。
- Redis 请求。
- MQ 请求。
- 第三方 API。
- 文件上传下载。

没有超时的调用可能一直卡住，占满线程、连接池和内存。

### 灰度和回滚

灰度：

- 按用户 ID。
- 按租户。
- 按地区。
- 按流量比例。
- 按内部账号。
- 按功能开关。

回滚要考虑：

- 代码能不能回滚。
- 配置能不能回滚。
- 数据库变更能不能回滚。
- 前端资源能不能回滚。
- 新旧版本数据是否兼容。

最危险的是不可逆数据库变更。生产发布尽量先兼容旧逻辑，再发布新逻辑，最后清理旧字段。

## 监控告警

### RED 指标

适合看服务和接口：

| 指标 | 含义 |
| --- | --- |
| Rate | 请求量 |
| Errors | 错误数或错误率 |
| Duration | 请求耗时 |

### USE 指标

适合看资源：

| 指标 | 含义 |
| --- | --- |
| Utilization | 使用率 |
| Saturation | 饱和度 |
| Errors | 错误数 |

看：

- CPU。
- 内存。
- 磁盘。
- 网络。
- 连接池。
- 队列堆积。
- 数据库连接数。
- Redis 内存。

### 日志、Trace、Metrics

日志要包含：

- 请求 ID。
- 用户 ID。
- 订单 ID。
- 接口名称。
- 错误类型。
- 关键业务状态。
- 下游调用结果。
- 异常堆栈。

Trace 用来查一次请求慢在哪里。

Metrics 用来看趋势和告警。

不要只写：

```text
error
failed
system exception
```

这种日志没有排查价值。

### 告警疲劳

告警不是越多越好。

好告警应该：

- 有明确影响。
- 有明确负责人。
- 有明确处理建议。
- 能区分严重程度。
- 能聚合重复告警。
- 能说明哪个服务出了什么问题。

不要为“看起来异常”告警，要为“用户体验或业务结果受影响”告警。

## 常见坑

- 只有备份，没有恢复演练。
- 没有超时。
- 重试风暴。
- 缓存击穿。
- 单点依赖。
- 第三方 API 不可用。
- 死信队列无人处理。
- 监控只有 CPU，没有业务指标。
- 告警没有负责人。
- 回滚方案没有演练。

## 一句话总结

从 0 到 1 的产品不需要一开始就做复杂灾备。

但至少要做到：

```text
知道哪里会坏。
知道坏了怎么恢复。
知道最多能丢多少数据。
知道多久必须恢复。
有人能收到告警。
有人能按文档处理。
```
