# 前言：为什么 AI 时代更需要技术栈判断力

AI 会让写代码变快，但不会自动让技术判断变正确。

很多时候，AI 可以给你生成一个能跑的项目，却很难替你承担这些后果：

- 数据模型选错后，后面每个功能都绕路。
- 把缓存当数据库后，线上数据开始不一致。
- 没有超时和幂等，第三方服务一抖动就全链路雪崩。
- 过早上微服务，团队每天都在处理分布式复杂度。
- Python 多线程被误用在 CPU 密集任务上，性能没有变好。
- 没有备份恢复演练，真正事故时才发现备份不可用。

这些不是“会不会写代码”的问题，而是技术栈判断力的问题。

## 这本书写什么

TechStack Compass 试图把产品工程里的隐性知识写成一本书。

它关心的不是：

```text
哪个技术最流行？
哪个语言最强？
哪个框架最现代？
```

它关心的是：

```text
这个业务现在最重要的约束是什么？
这个技术解决的真实问题是什么？
它带来的隐藏成本是什么？
什么时候该用，什么时候不该用？
如果线上出事，系统能不能恢复？
```

## 为什么叫 Compass

因为真实工程里很少有永远正确的答案。

技术选择更像导航：

- 你要知道自己在哪里。
- 你要知道目标是什么。
- 你要知道路上最大的风险是什么。
- 你要知道什么时候该走快，什么时候该保守。

这本书不是替你做所有选择，而是帮你建立方向感。

## 第一性原理

本书尽量从第一性原理出发。

技术栈不是“技术名词列表”，而是对几个基本约束的取舍：

- 计算：CPU、I/O、网络、数据处理到底谁是瓶颈。
- 状态：数据是否长期保存，是否需要事务，是否允许丢。
- 反馈速度：写完代码到验证真实用户需要多久。
- 风险：哪个错误最不能接受，是数据错、服务挂，还是成本爆。
- 成本：机器、人力、学习、维护、迁移，哪个最贵。
- 团队能力：团队能不能正确使用、排查和交接。
- 可替换性：这个选择未来换起来有多难。

如果一个技术选择不能回到这些约束，就很容易变成跟风。

## 这本书不是什么

它不是“最全技术大全”。

它也不是“高星项目包装教程”。

项目目标是成为高星知识库，但路径不是包装，而是内容本身值得收藏。

如果读者在真实项目里遇到问题时会回来查，这个项目才有机会变成高星。
